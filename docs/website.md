# The website (perritodeck.dev)

The source is in [`website/`](../website/). GitHub Pages serves the site from a separate
public repository, `perritodeck/perritodeck.github.io`, which holds only what
[`scripts/publish_site.py`](../scripts/publish_site.py) builds from `website/` and `plugins/`
here (D12 in [`DECISIONS.md`](DECISIONS.md), 2026-10-17; see [Deploy](#deploy)). It has
done so since the cutover on 2026-10-24 ([Cutover runbook](#cutover-runbook)). Every file in
`website/` is published, so notes about the site live here instead: this file used to be
`website/README.md`, which was live at `https://perritodeck.dev/README.md`. File names in
the first sections are in `website/`, except `plugins/build_catalog.py`,
`plugins/test_build_catalog.py` and those starting with `docs/`, `host/` or `scripts/`.

Plain HTML and CSS, no build step, no framework and no third-party requests. JavaScript is
used only where it adds something: the demo deck on the home page (`deck.js`), the download
page picking out your system (`download.js`), and the plugin catalogue's search box
(`catalogue.js`). Every page works without it.

| Page | What |
|---|---|
| `index.html` | Home: what it is, the three use cases, how it works, the demo deck, where it stands |
| `features.html` | What it does, with app screenshots |
| `compatibility.html` | Stream Deck plugins and Bitfocus Companion: what works and what doesn't yet |
| `faq.html` | Questions people ask before trying it |
| `download.html` | Downloads, requirements, checking a download, building from source. Its version is updated by `scripts/release-version.py` |
| `privacy.html` | The privacy policy the store listings link to. Keep it matching what the apps do |
| `guide/` | The user guide. It changes in the same commits as the features it describes |
| `plugins/` | Generated by the top-level `plugins/build_catalog.py` (not committed; each publish builds it): the catalogue page, `index.json` for the app, and one zip per plugin. The page's style and script are the committed `catalogue.css` and `catalogue.js` |
| `404.html` | The page for any address that doesn't exist, which GitHub Pages serves with a 404 status |
| `robots.txt`, `sitemap.xml` | For search engines. Add new pages to the sitemap |

Every page shares the header and footer markup; copy them from an existing page when adding
one, and mark the current section with `aria-current="page"`. `404.html` is the exception:
it can be served at any depth, so its links start with `/`.

Every page's `<head>` starts with `<meta charset>` and then the policy tags, before
anything else, since a policy covers only what comes after it: the Content-Security-Policy,
the referrer policy and, on `404.html` only, `robots` noindex ([Headers and
policies](#headers-and-policies)). It also has a canonical link and the tags link previews
use (Open Graph and `twitter:card`): the page's own address on `https://perritodeck.dev`
without `.html` (folders end in `/`), the same title and description as the page, and the
preview image `https://perritodeck.dev/img/og.png`. Copy them too when adding a page, change
the address, title and description, and add the address to `sitemap.xml`. `404.html` has no
canonical link or preview tags, because it answers at any address. The catalogue page's
`<head>` is in the template in `plugins/build_catalog.py`.

**No inline code.** The site's Content-Security-Policy allows only files from the site
itself, so a `<script>` without `src`, a `<style>` block, a `style="…"` attribute or an
`onclick` would silently stop working. Put scripts in a `.js` file and styles in
`style.css`, `guide/guide.css`, `download.css` or `catalogue.css`. The same goes for the
catalogue template in `plugins/build_catalog.py`. `plugins/test_build_catalog.py` checks
every page, that each script, stylesheet and image a page loads exists, and that the
stylesheets' `url(…)` and `@import` point only at files in `website/` (no `data:` URIs, no other
sites). It checks that every page and the catalogue template start with the three policy
tags, each exactly once, and that the `<meta>` CSP is the test's `POLICY`, which it checks
is strict: `default-src 'none'`, and no `unsafe-`, hashes, nonces, `*`, `http:`, `https:`
or `data:`. It also checks that each page's canonical link, link-preview tags and
`sitemap.xml` entry agree, and that the preview image exists at the size the tags give.

**Only files the site serves.** `website/` holds pages, stylesheets, scripts, images, fonts
with their licence files, `robots.txt` and `sitemap.xml`. Notes go in this file and
scripts in `scripts/`, because anything else in `website/` would be published too. The same
test fails on any other kind of file there (it skips the generated `plugins/`); if the site
needs a new kind of file, add it to the test's list. `scripts/publish_site.py` also refuses
to publish a `.md` file, or Cloudflare's `_headers` and `_redirects`, which GitHub Pages
would serve as files.

## Fonts and images

- `fonts/`: Bricolage Grotesque (variable, weight and optical size) and Atkinson Hyperlegible
  (regular and bold), latin subsets from the Fontsource packages, under the SIL Open Font
  License (licence files alongside). `style.css` declares them.
- `img/`: WebP made from the PNG masters with Pillow at quality 90, alpha kept. The masters
  are in `docs/assets/site/` (the device mockups, scaled to 1400 or 1100 px wide) and
  `docs/assets/screenshot-*.png` (the app, light and `-dark`, scaled to 1600 px into
  `img/app/`). Pages show the dark screenshots with `<picture>` when the system is dark.
- `paw.svg` is `docs/assets/icon-master-rounded.svg`, the app icon. `favicon.ico` (16, 32 and
  48 px, for browsers that don't use the SVG) is `docs/assets/icon-rounded-1024.png`
  scaled with Pillow. `apple-touch-icon.png` (180 px) is the square `icon-1024.png` instead,
  because iOS rounds the corners itself and turns transparent ones black.
- `img/og.png` (1200 × 630) is the picture link previews show, named by every page's
  `og:image`. It's a PNG because every service that shows link previews accepts PNG and
  JPEG, while WebP isn't safe everywhere. Keep it under about 300 KB, since some chat apps
  skip larger previews (it's about 220 KB). [`scripts/og-image.py`](../scripts/og-image.py)
  makes it with Pillow: on the light theme's `--fog` with a soft `--apricot` glow,
  `docs/assets/site/devices-hero.png` scaled to 700 px wide on the right, and on the left
  `docs/assets/icon-rounded-1024.png` at 72 px, the name, the home page's tagline, "Free and
  open source. No account, no cloud." and `perritodeck.dev` in `--apricot-deep`. The text is
  Inter SemiBold (`host/crates/render/assets/Inter-SemiBold.otf`, SIL Open Font License),
  because Pillow can't read the site's woff2 fonts. Remake it with
  `python3 scripts/og-image.py` (`py -3` on Windows) when the hero picture, the icon or the
  tagline changes. With the same Pillow it writes the same bytes, so a run with nothing
  changed leaves git clean.

Quality bar: works at phone width (375 px) and wide (1440 px), in light and dark, with
visible keyboard focus, and each page under about 200 KB before images.

## Preview

```sh
cd website && python3 -m http.server 8000   # then open http://localhost:8000
python3 plugins/build_catalog.py website/plugins   # to preview the plugin catalogue too
```

The policies are `<meta>` tags, so the browser applies the CSP in a preview too: a console
error there is one the live site would show. `python3 -m unittest test_build_catalog` in
`plugins/` catches inline code before then, and CI runs it (the Plugins and Site publish
workflows) on every change under `website/`. A new build of the catalogue into
`website/plugins` replaces the last one's zips and icons, so no old version lingers;
`build_catalog.py` refuses a folder that isn't empty and holds no catalogue. It reads each
file's mode from git, so on Windows `git` must be Git for Windows
(`(Get-Command git).Source`).

## Deploy

GitHub Pages serves the site from the public repository `perritodeck/perritodeck.github.io`:
an organization site, **Deploy from a branch**, `main`, `/ (root)`, with a `CNAME` file
naming `perritodeck.dev` and an empty `.nojekyll` (without it, Jekyll would leave out files
whose names start with `_` or `.`). Cloudflare does only the domain's DNS ([The
domain](#the-domain)). That's how evi-ai.dev, the maintainer's other project's site, works
(D12, 2026-10-17). The canonical address is the bare domain, `https://perritodeck.dev` (no
`www`), which is what the app's catalogue URL (`https://perritodeck.dev/plugins/index.json`)
and every link in the repository use.

**The site repository holds generated output only.** `website/` here is the one source.
Never edit the site repository by hand, and don't add a README to it: the next publish
deletes anything that isn't in the build, and Pages would serve a README at `/README.md`.
Only `CNAME` and `.nojekyll` are kept from what's there.

### What a publish does

`scripts/publish_site.py <clone of the site repository>`, standard library only:

1. It refuses a working tree with changes, a `HEAD` that isn't `origin/main` (`git fetch`
   first), and a folder that isn't a clone of `perritodeck/perritodeck.github.io`.
2. It builds from a fresh checkout of `HEAD` (a `git clone --shared`, which writes nothing
   into this repository), so no untracked or git-ignored file goes out, not even a `.env` in
   a plugin's folder, which `build_catalog.py` would zip. `website/` is copied as it is,
   and the catalogue is built into a new folder and published as `plugins/`, where Look
   online downloads it.
3. It makes the site clone hold exactly that: everything else is deleted, empty folders too,
   `.git` is left alone, and `CNAME` and `.nojekyll` are kept or created.
4. It checks the result: it matches the build byte for byte, the required pages are there,
   `plugins/index.json` parses and every zip it lists is beside it with its SHA-256, `CNAME`
   says `perritodeck.dev`, and no `_headers`, `_redirects` or `.md` file would be served.
5. It prints the site clone's `git status` and the commands that commit and push it. It
   never commits or pushes.

`--verify` builds and checks the same way without the guards in step 1, into a new or empty
folder (or one an earlier run filled); pull requests use it. `--check-live` is the drift
check ([The domain](#the-domain)). The script's tests: `python3 -m unittest test_publish_site`
in `scripts/` (`py -3` on Windows, with Git for Windows as `git`).

The catalogue is built from `main` (D3), at each publish.

### Publishing by hand, until the flip

Actions don't run until the repository is public (DECISIONS, 2026-10-15), so until then a
site update means running the script by hand after each change to `website/` or `plugins/`
on `main`. Do it in WSL, from clones on Linux's own disk: WSL's git refuses a Windows
checkout under `/mnt` as "dubious ownership". Claude can run it and show the result; each
push waits for the maintainer's OK.

Once, in WSL (Ubuntu): two clones side by side, each with the maintainer's identity and
dmang-dev's credential set in it, since WSL doesn't read the Windows `~/.gitconfig` that
picks them by folder there. The credential comes from the Windows `gh` (`gh.exe`, through
WSL's interop), whichever account is active in it:

```sh
mkdir -p ~/site && cd ~/site
auth='!f() { if [ "$1" = get ]; then echo username=dmang-dev; echo "password=$(gh.exe auth token --user dmang-dev | tr -d "\r")"; fi; }; f'
git -c credential.helper= -c credential.helper="$auth" clone https://github.com/perritodeck/perritodeck.git
git clone https://github.com/perritodeck/perritodeck.github.io.git
for r in perritodeck perritodeck.github.io; do
  git -C "$r" config user.name dmang-dev
  git -C "$r" config user.email dev@perritodeck.dev
  git -C "$r" config credential.helper ''              # forget any inherited helper first
  git -C "$r" config --add credential.helper "$auth"
done
```

Each publish:

```sh
cd ~/site
git -C perritodeck pull --ff-only             # main, as it is on GitHub
git -C perritodeck.github.io pull --ff-only   # Settings → Pages commits there too (skip on the first publish: it's empty)
python3 perritodeck/scripts/publish_site.py perritodeck.github.io
```

Read the `git status` it prints. Then, with the maintainer's OK, run the commands it prints
(`git add -A`, `git commit -s -m "site: publish from perritodeck@<sha7>"` and `git push`, each
with `-C perritodeck.github.io`), and check the author with
`git -C perritodeck.github.io log -1 --format='%an <%ae>'` (`dmang-dev <dev@perritodeck.dev>`).
The first push goes to an empty repository: run `git -C perritodeck.github.io branch -M main`
before it, and push with `git -C perritodeck.github.io push -u origin main`. GitHub's own
`pages-build-deployment` workflow in the site repository then publishes it
(`gh run list --repo perritodeck/perritodeck.github.io --limit 3`).

### After the flip: Site publish

[`.github/workflows/site-publish.yml`](../.github/workflows/site-publish.yml) runs the same
script, the way evi's `docs-publish.yml` does:

- On a push to `main` touching `website/**`, `plugins/**` (not `plugins/tools/**`), the
  script, its test or the workflow, it runs `test_publish_site` and `test_build_catalog`,
  checks out the site repository with `SITE_PUBLISH_TOKEN`, publishes into it, then commits
  as `perritodeck-site-bot <noreply@github.com>` with "site: publish from
  perritodeck@<sha7>" and pushes, or prints "site: no change".
- Pull requests, other branches and runs before the token exists build and check into a
  stand-in folder (`--verify`) and push nothing, so a page that would break fails review
  instead of going live. **Run workflow** publishes again without a change.
- Two publishes never run at once, and none is cancelled halfway (concurrency group
  `site-publish`). Pull requests and runs from other branches only build, so each ref but
  `main` gets a group of its own and can't take the place of a pending publish.
- `GITHUB_TOKEN` can't push to another repository, hence `SITE_PUBLISH_TOKEN`. It's a secret
  of the `site` environment, which only `main` may deploy from, and only a run on `main`
  that isn't a pull request asks for that environment. Make it a fine-grained personal
  access token with the perritodeck organization as resource owner, access to
  `perritodeck.github.io` only and Contents read and write, and write its expiry in the
  [launch checklist](launch-checklist.md) (§4): it belongs to the maintainer's account and
  runs out. A deploy key with write access on the site repository is the narrower
  alternative (one repository, no expiry, not tied to a person); the workflow's site
  checkout would then pass `ssh-key:` instead of `token:`.

### Before the cutover

From 2026-10-15 to 2026-10-24 a Cloudflare Worker named `perritodeck` (static assets, set up
in the dashboard, with `perritodeck.dev` as its custom domain) served the site. Pushes to
`main` redeployed it, it sent the headers in a `website/_headers` file (the CSP with
`frame-ancestors`, a two-year HSTS header, `Cache-Control: no-transform`, the temporary
`X-Robots-Tag: noindex` and the rest), and a Redirect Rule on a proxied placeholder record
sent `www` to the bare domain. It answered unknown addresses with an empty 404 instead of
`404.html`. The Worker was deleted at the swap on 2026-10-24, and `_headers` the same day.
The zone settings that act only on proxied traffic (the SSL/TLS mode, Web Analytics, Email
Address Obfuscation, Rocket Loader, Bot Fight Mode, Speed Brain, Browser Cache TTL) were
never confirmed in the dashboard. Nothing for the site passes through Cloudflare any more,
so they don't matter; leave them as they are.

### The domain

DNS is at Cloudflare (nameservers `aida` and `algin.ns.cloudflare.com`, since 2026-10-13),
the registrar is Namecheap, and since the cutover (2026-10-24) the site's records are:

| Name | Type | Value | Proxy |
|---|---|---|---|
| `perritodeck.dev` | `A` | `185.199.108.153`, `185.199.109.153`, `185.199.110.153`, `185.199.111.153` | DNS only |
| `perritodeck.dev` | `AAAA` | `2606:50c0:8000::153`, `2606:50c0:8001::153`, `2606:50c0:8002::153`, `2606:50c0:8003::153` | DNS only |
| `www` | `CNAME` | `perritodeck.github.io` | DNS only |
| `_github-pages-challenge-perritodeck` | `TXT` | the value GitHub gave when the domain was verified | DNS only, kept for good |

**Never set the apex or `www` records to proxied (the orange cloud).** GitHub can't renew
its certificate while Cloudflare's proxy sits in front, so the site dies when the current
certificate expires, at most 90 days later. Lowering Cloudflare's SSL mode to Full (not
strict) doesn't fix that; it only hides it by accepting an invalid certificate. That's
exactly what happened to evi-ai.dev: its records were switched to proxied against its own
docs, GitHub's certificate expired on 2026-09-30, and the site answered Cloudflare's error
526 from then until its records went back to DNS only on 2026-10-17, with nobody noticing
for weeks.

GitHub does the rest by itself: `http://` answers 301 to `https://` (Enforce HTTPS),
`www` answers 301 to the bare domain keeping the path and query, `perritodeck.github.io`
answers 301 to the domain, unknown addresses get `404.html` with a 404 status, and its Let's
Encrypt certificate covers the apex and `www` and renews itself (the first runs until
2027-01-22).

**The drift check**, `python3 scripts/publish_site.py --check-live`, catches a proxy switched
back on long before the certificate runs out. It fails unless `perritodeck.dev` and `www`
resolve only to GitHub Pages' addresses, `/` and `/plugins/index.json` answer 200 and `www`
answers 301 to the bare domain, all with `Server: GitHub.com` (it names Cloudflare when
that's what answered), and the certificate has more than 21 days left; the 21 days assume
90-day certificates, so lower `CERT_DAYS` in the script if Let's Encrypt's get shorter.
After the flip the Site check workflow
([`site-check.yml`](../.github/workflows/site-check.yml)) runs it every Monday and on
**Run workflow**; until then, run it by hand. It never skips itself: an address that isn't
GitHub's fails it, whatever answers there.

The weekly run doesn't read the Pages API's certificate state, which would show a failed
renewal (`bad_authz`) sooner than the 21 days: that endpoint needs a token with access to the
site repository's Pages settings (without one it answers 404, even for a public repository),
and `GITHUB_TOKEN` covers only this repository. One more secret isn't worth the weeks it
would gain, since a proxied record already fails the DNS and `Server` checks the same day.
By hand, also check that
`gh api repos/perritodeck/perritodeck.github.io/pages --jq .https_certificate.state` says
`approved`.

**DNSSEC** has been in force since 2026-10-15, with the `DS` record (key tag 2371,
algorithm 13, digest type 2) at the `.dev` registry (`Resolve-DnsName perritodeck.dev -Type
DS -Server 1.1.1.1`, or `dig +short DS perritodeck.dev @1.1.1.1`, prints it). Cloudflare
signs every record in the zone, so edits need nothing more. If the domain ever moves away
from Cloudflare's nameservers, remove the DS record at the registrar first, or the domain
stops working.

**Mail records** (by 2026-10-15): `MX` to ImprovMX, SPF
(`v=spf1 include:spf.improvmx.com ~all`), one `_dmarc` record (`p=none`, aggregate reports
to Cloudflare's DMARC Management) and ImprovMX's two DKIM `CNAME` records. A domain has only
one SPF record, and two make both fail: for a new sender, edit it rather than adding one.

**Mail for `dev@perritodeck.dev`** (D2 in [`plan/phase-8.md`](plan/phase-8.md), decided
2026-10-15): ImprovMX forwards it to the maintainer's mailbox, and replies as `dev@` go out
through Gmail's "Send mail as" and Gmail's own SMTP, which fails DMARC alignment for the
domain, so DMARC stays at `p=none` (`p=reject` would bounce those replies). Google ends
"Send mail as" for custom domains in January 2027, so before then replies need ImprovMX
Premium's SMTP (its DKIM records are already in DNS) or a free SMTP relay, either of which
lets DMARC go to `p=reject`.

Cloudflare's own HSTS and Network Error Logging settings were turned off on 2026-10-15, so
that visitors' browsers send Cloudflare no reports. Both act only on proxied traffic, so
they don't touch the site.

The privacy policy's address is `https://perritodeck.dev/privacy`, the address its canonical
link gives (GitHub Pages serves the same page at `/privacy.html` too). That's the one for
the store listings, and for Play Console's privacy policy field if Google Play is ever used
(not for now, D8 in `docs/plan/phase-8.md`).

### Headers and policies

- GitHub Pages doesn't let a site set response headers. By default it sends no CSP, HSTS,
  `X-Content-Type-Options`, `X-Frame-Options` or `X-Robots-Tag`, and `Cache-Control:
  max-age=600` on everything, with an `ETag`, `Last-Modified`, `Access-Control-Allow-Origin:
  *` and the right content types.
- So the policies are `<meta>` tags, right after `<meta charset>` in every page and in the
  catalogue template:
  `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; base-uri 'none'; form-action 'none'">`,
  and `<meta name="referrer" content="no-referrer">`, plus `<meta name="robots"
  content="noindex">` on `404.html` only. Copy them from an existing page when adding one;
  `plugins/test_build_catalog.py` checks that they're first, each there once, and that no
  other page has a robots tag.
- There's **one** CSP. Two would be two policies that must both pass. It has no
  `frame-ancestors`, which browsers ignore in a `<meta>` tag (and warn about). The test
  holds it as `POLICY`, so a change goes there, in every page and in the catalogue template
  together.
- The policy allows scripts, styles, fonts and images from the site itself and nothing else:
  no inline code (see the top of this file), no other sites, no `fetch`. Anything from
  elsewhere, such as a web font service, an embed or analytics, is blocked until the policy
  says otherwise, and then `privacy.html` needs updating too.
- `robots` noindex kept search engines out until launch and came off every page but
  `404.html` on launch day (2026-10-25). `robots.txt` allows everything, because a
  `Disallow` would keep crawlers from ever reading a noindex.
- Given up with the move (D12): framing protection (`frame-ancestors`, `X-Frame-Options`),
  so another site could show the pages in a frame; `X-Content-Type-Options: nosniff`; the
  `Permissions-Policy` that turned off the camera, microphone, location, payments and USB;
  `Cross-Origin-Opener-Policy`; the long cache lifetimes, so fonts and images are checked
  again after 10 minutes; and noindex on files that aren't pages (`index.json`, the zips,
  images). The site has no forms, sign-in or anything that runs on a server, so these were
  extra protection rather than something it relies on. The HSTS header goes too, which
  changes nothing in browsers: every `.dev` domain is on their HSTS preload list. (GitHub
  sends HSTS for some custom domains; it can be asked for.)
- `Cache-Control: no-transform` isn't needed any more: with DNS only, nothing sits between
  GitHub and the browser to inject a beacon or challenge Look online.
- There's no `_headers` file any more (it went with the Worker, 2026-10-24). Don't add one,
  or a `_redirects`: GitHub Pages would serve it as a file, so the folder test and the
  publish both fail on it.
